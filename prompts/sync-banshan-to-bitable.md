# 搬山用例同步飞书多维表格 · 执行 Prompt

## 使用方式

复制下方 Prompt 给 Claude，替换 `<>` 中的参数后发送。

---

## Prompt 正文

```
将搬山用例 caseId=23515 同步到飞书多维表格。

目标表格：https://gaotuedu.feishu.cn/base/FqOdbfKtAaOwIys9zZXcrH6EnFf?table=tblZ0fn48cchDE6Y&view=vew8U8Ocwy

固定字段（所有用例相同）：
- 小组: 社区
- 模块: 首页
- Android设备 / ios设备: 留空
- 是否自动化执行: 默认 false，见 Step 5 规则

模式：快速（可选，默认标准）
```

> **模式说明**
> - **标准模式**（默认）：执行 Step 3 确认过滤范围 + Step 8 展示列表等待确认，再写入
> - **快速模式**：跳过 Step 8，完成 Step 3 确认后直接解析并写入，仅在 Step 10 报告中展示优化与标记详情

---

### Step 1 · 解析飞书链接，获取 app_token 和 table_id

从「目标表格」链接中提取参数：

**情况一：直接多维表格链接**
```
https://*.feishu.cn/base/{app_token}?table={table_id}
```
直接从 URL 截取 app_token 和 table_id。

**情况二：Wiki 页面链接**
```
https://*.feishu.cn/wiki/{wiki_token}?table={table_id}
```
调用 `wiki_v2_space_getNode(token=wiki_token)`，取返回值中的 `obj_token` 作为 app_token；
table_id 直接从 URL 的 `table=` 参数截取。

---

### Step 2 · 读取用例树

调用 `testCaseDetail(caseId)`，解析 `caseContent` JSON，提取 root 节点。

---

### Step 3 · 展示结构，确认过滤范围

展示前三层节点，每行标注该子树下叶子节点数，例如：

```
1. 前置数据准备（4 条）
  1.1 一、创建课程...（1 条）
  1.2 二、创建CES课节...（1 条）
2. 学生端进入C端学习（48 条）
  2.1 首页大卡展示（3 条）
  2.2 课节列表（15 条）
```

询问用户：

> 以上哪些节点及其子树**不需要同步**？
> 请回复节点序号（如 1、2.1），多个用逗号分隔，全部同步则回复 0。

等待用户回复后，将指定节点及其所有子节点标记为 SKIP，后续不处理。

---

### Step 4 · 遍历叶子节点，合并与收集路径

遍历剩余节点树，找出所有**叶子节点**（children 为空）。

**合并规则**：同一父节点下的多个兄弟叶子节点，满足以下任意条件时，合并为一条用例：

| 条件 | 合并方式 |
|------|----------|
| 兄弟叶子全部为 ASSERT 类型 | 父节点作为用例主体，所有兄弟文字合并为预期结果（换行分隔） |
| 兄弟叶子全部为 ACTION 类型（顺序步骤） | 父节点作为用例主体，所有兄弟文字按序合并为测试步骤 |
| 兄弟叶子为 ACTION + ASSERT 的组合 | 合并为一条用例，ACTION 归步骤，ASSERT 归预期结果 |

**不合并的情形**：
- 兄弟叶子各自有不同的 LABEL / 测试点标签（代表不同场景）
- 兄弟叶子文字明显描述不同入参或不同操作对象（如「按钮A」「按钮B」）

合并后的节点组 = 一条用例，记录从 root 到父节点的路径，加上所有兄弟叶子内容，有序保存。
未合并的叶子节点仍各自为一条用例，记录完整祖先路径。

---

### Step 4.5 · 并行分批（用例数 > 50 时）

收集到所有叶子节点路径后，若总数 **> 50 条**，按顺序均分为若干批（每批不超过 50 条），为每批启动一个子 Agent 并行执行 Step 5 → Step 9：

- 每个子 Agent 独立完成：节点分类 → 字段提取 → 质检改写 → 写入飞书
- 子 Agent 写入时使用相同的 app_token、table_id 和固定字段
- 快速模式下子 Agent 直接写入，标准模式下各子 Agent 先返回用例列表，汇总后统一确认再写入
- 所有子 Agent 完成后，主流程汇总各批结果，进入 Step 10 输出报告

总数 ≤ 50 条时，单 Agent 顺序执行，不分批。

---

### Step 5 · 对路径中每个节点分类

按优先级判断，每个节点归入一类（同一节点可归入多类）：

| 优先级 | 判断条件 | 分类 |
|--------|----------|------|
| 1 | resource 含「预期结果」 | **ASSERT** |
| 2 | resource 含「前置条件」 | **PRECOND** |
| 3 | resource 含「执行步骤」 | **ACTION** |
| 4 | resource 含「功能点」或「测试点」，且不含以上三类 | **LABEL**（贡献用例名称，不生成步骤） |
| 5 | resource 为空，且是**叶子节点** | 按语义判断：结果/状态描述→ASSERT；操作动词开头→ACTION；条件描述（若/当/已）→PRECOND |
| 6 | resource 为空，且是**非叶子节点** | **CONTEXT**（仅用于命名上下文，不写入字段） |

同一节点同时含「执行步骤」+「预期结果」时，其文字同时贡献给 ACTION 和 ASSERT。

**自动化标记处理规则：**

- resource 含「可ui自动化」：该用例「是否自动化执行」= true，判断范围为整条路径（路径上任意节点含该标记均生效）
- resource 含「可接口自动化」：忽略，不影响该字段
- 其余节点的其他 resource 标签照常分类（ASSERT / ACTION / PRECOND 等）

**优先级标记处理规则：**

优先级来源有两种，同时检查，取最高级（P0 > P1 > P2）：

| 来源 | 说明 |
|------|------|
| 节点 `priority` 字段 | 1 → P0，2 → P1，3 → P2 |
| 节点 `resource` 含「p0」「p1」「p2」 | 不区分大小写直接映射 |

- 判断范围为整条路径（路径上任意节点命中均生效）
- 若路径上无任何优先级标记，该字段不传（留空）

---

### Step 6 · 提取各字段

**用例名称**

从路径中筛选出有语义价值的 CONTEXT / LABEL 节点，按层级拼接为「模块 - 功能 - 场景」结构：

1. **筛选关键节点**：跳过纯序号、重复上层语义、过于宽泛（如「正向」「异常」）的节点；保留能区分场景的关键词节点
2. **拼接规则**：取 2～4 个关键节点文字，用「-」连接，整体不超过 30 字
3. **末尾补充叶子语义**：若叶子节点文字能补充具体动作或结果（且未被上层覆盖），追加到末尾
4. **去重**：相邻节点含义重复时只保留更具体的一个
5. **兜底**：若路径节点均无法组合出有意义名称，取倒数第二层 + 叶子节点文字

示例：
- 路径：学生端 → 首页 → 大卡展示 → 课程顺序 → 按报名时间排序  
  → 用例名称：`首页大卡-课程顺序-按报名时间排序`
- 路径：教师端 → 课节列表 → 添加老师 → 按钮展示  
  → 用例名称：`课节列表-添加老师按钮展示`

**预置条件**
- 路径中所有 PRECOND 节点文字，按层级顺序拼接，`\n` 分隔
- 若路径无 PRECOND，根据最顶层 ACTION 语境补写当前入口状态，如「已进入课程班级课节列表」
- **链路用例**：若多个叶子节点为同级兄弟且语义上构成顺序流程，从第二条起前置条件写「已完成上一步：[上一条用例名称或操作]」，不重复写进入首页/打开 App 等初始入口

**测试步骤**
- 路径中所有 ACTION 节点文字，按层级顺序加序号，每条独占一行（用换行符分隔），格式：`1. xxx\n2. xxx\n3. xxx`
- 若单个 ACTION 节点内含多个并列操作（用「；」或换行分隔），拆分为多个子步骤，各占一行

**预期结果**
- 路径中所有 ASSERT 节点文字，每条独占一行（用换行符分隔），格式：`xxx\nxxx`
- 叶子节点通常是最终 ASSERT，内容权重最高

**验证点**
- 从预期结果提炼 1~3 个核心可观测验证点，一行一条
- 描述格式：界面可见状态，如「按钮展示'查看报告'」、「跳转到XX页面且内容正常加载」

**优先级**
- 扫描整条路径，同时检查节点 `priority` 字段（1=P0, 2=P1, 3=P2）和 `resource` 标签（p0/p1/p2），取最高级
- 写入飞书时使用对应选项值（单选）：`P0` / `P1` / `P2`
- 路径上无任何优先级标记时不传该字段

**用例备注**
- 节点 note 字段非空时填入；否则不传该字段

### Step 7 · 内容质量自检、改写与自动化可行性评估（批量处理，不逐条输出）

**A. 内容改写**（发现后自动改写并标记 ⚠️）

| 问题类型 | 示例 | 改写方向 |
|----------|------|----------|
| 预期结果空泛 | 「展示正常」「功能正常」 | 结合路径推断具体状态，如「页面展示课节列表，课节1显示已完成（✅）」 |
| 预期结果缺少主语 | 「展示对勾」 | 补全主语：「单课节右侧展示对勾✅」 |
| 预期结果为纯过程描述 | 「点击后跳转」 | 改为结果：「跳转至XX页面，页面内容正常加载」 |
| 前置条件引用用例编号 | 「参考用例X」 | 替换为对应的页面/数据状态描述 |
| 前置条件仅写入口 | 「进入首页」 | 补充「当前页面显示...」等具体状态 |
| 步骤混入结果 | 「点击后跳转到...」 | 步骤保留「点击XX」，结果移入预期结果 |

**B. 自动化可行性评估**（命中则在「用例备注」写入 `【需人工修改】原因：...`，并标记 🔴）

| 编号 | 情形 | 判断方式 | 备注示例 |
|------|------|----------|----------|
| F1 | 无测试步骤 | ACTION 节点为空且无法从路径推断 | 无法解析操作步骤，需人工补充 |
| F2 | 无预期结果 | ASSERT 节点为空且路径无法推断 | 无断言内容，无法自动化验证 |
| F3 | 预期结果改写后仍不可验证 | 改写后仍含「正常」「无异常」等，无具体 UI 状态 | 预期结果不具体，需明确可截图验证的状态 |
| F4 | 步骤依赖非 App 端操作 | ACTION 含 OES/CES/阿波罗/数据库/后台配置等 | 步骤含后台系统操作（[系统名]），无法 UI 自动化 |
| F5 | 前置条件依赖不确定数据状态 | PRECOND 含「若...」「配置了...」但未给出具体数据值 | 前置条件未指定具体测试数据，需明确 |
| F6 | 一条用例含多个分支场景 | 路径含多个平行 ASSERT，或步骤含「若A则...若B则...」 | 用例含条件分支，建议拆分为多条 |
| F7 | 无法定位到具体 UI 场景 | 改写后名称仍为泛称，路径上下文不足以补全 | 描述过于笼统，无法确定对应 UI 场景 |

一条用例可同时命中多条，备注中列出所有原因（逗号分隔）。
🔴 标记的用例仍正常写入 Bitable，`是否自动化执行` 不因标记强制改为 false。

# 用例首次通过后固化脚本设计

## 背景

当前自动化主流程以 agent 为主执行器：

- 编排器从飞书多维表拉取自动化用例
- 按设备分组、按设备内顺序执行
- agent 根据自然语言步骤和页面上下文逐条执行

这套链路覆盖面高，但有两个明显问题：

1. 同一条稳定用例每次都重新“理解并执行”，成本高且不稳定。
2. 已跑通的稳定路径没有沉淀为可复用资产，后续版本回归仍高度依赖 agent 即时决策。

目标是在不替换现有 agent 主链路的前提下，引入“首次通过后固化脚本、后续优先跑脚本”的能力。

## 目标

本设计要实现：

- 仅对首次执行通过的用例生成脚本
- 一条用例对应一个独立脚本文件
- 后续执行时优先跑脚本
- 脚本失败时自动回退 agent
- agent 回退执行通过后，覆盖或重生成该脚本

本设计阶段只覆盖 Android。

## 非目标

本阶段不做：

- iOS 脚本化
- 失败用例自动固化
- 纯视觉低可信断言的脚本化
- 全量录制回放
- 跨设备共享复杂脚本状态
- 引入 pytest / robot / airtest 等新框架

## 方案选择

### 方案 A：结果落盘后生成 Python 脚本

第一次 agent 执行通过后，依据结果中的高可信证据与原始步骤生成 Python 脚本；后续优先跑该脚本，失败再回退 agent。

优点：

- 对现有 orchestrate 侵入最小
- 不要求 agent 在首跑时额外承担稳定脚本生成职责
- 可与现有 JSONL 结果落盘、批次执行机制自然衔接

缺点：

- 生成质量依赖结果结构是否足够稳定
- 低可信结果无法自动脚本化

### 方案 B：让 agent 首跑时直接输出脚本

优点是首跑上下文最全。缺点是 agent 输出面扩大，稳定性更差，且失败时难以区分“执行失败”和“脚本生成失败”。

### 方案 C：录制底层动作流后回放

优点是实现直观。缺点是回放对页面微小变化极其脆弱，不符合“稳定脚本”目标。

### 结论

采用方案 A。

## 总体设计

在现有编排器里新增两个能力：

1. 脚本生成器：从通过结果生成独立 case 脚本
2. 脚本执行器：执行前检查是否已有脚本，命中则优先执行

执行流程调整为：

1. 拉取飞书用例
2. 按设备分组，保持设备内原顺序
3. 对每条用例：
   - 若存在脚本，先执行脚本
   - 脚本通过，直接记结果
   - 脚本失败，记录失败原因并回退 agent
   - agent 通过，生成或覆盖脚本
   - agent 失败，不生成脚本

## 文件布局

新增脚本目录：

`apps/gaotu/cases/android/<record_id>.py`

例如：

`apps/gaotu/cases/android/recvj5aWyBoGh1.py`

单条脚本文件只对应一个 `record_id`，不按模块合并。

## 脚本结构

每个脚本文件包含：

- `META`
  - `record_id`
  - `name`
  - `module`
  - `platform`
  - `generated_at`
- `prepare(ctx)`
  - 处理账号前置
  - 处理未登录前置
  - 处理目标 tab / 页面前置
  - 处理需要重装的前置
- `run(ctx)`
  - 执行动作步骤
- `assertions(ctx)`
  - 只做高可信断言
- `execute(ctx)`
  - 统一串起 prepare / run / assertions

脚本输出统一结果对象，字段尽量与现有 case result JSON 兼容：

- `record_id`
- `name`
- `platform`
- `device`
- `module`
- `passed`
- `duration`
- `steps`
- `note`
- `script_source=script`

## 脚本生成规则

仅当满足以下条件才生成脚本：

- 该条 case 最终通过
- 关键断言存在高可信证据
- 所需前置可以稳定表达

高可信证据定义：

- `verify_method = id`
- `verify_method = text`

不自动脚本化的情况：

- 仅有 `vision + low confidence`
- 关键动作缺乏稳定 locator
- 当前结果依赖一次性线上态或外部环境

生成时保留：

- 原始 `PRECOND/ACTION/ASSERT` 的结构
- 结果中可验证的 selector / text evidence
- 必要等待和页面检查

生成时丢弃：

- 临时截图路径
- 临时 page source 文件路径
- 自然语言总结
- 一次性调试输出

## 执行器设计

新增脚本查找逻辑：

- 输入：`app_id + platform + record_id`
- 输出：脚本文件是否存在

新增脚本执行逻辑：

- 使用 Python 直接加载 case 脚本
- 向脚本传入统一执行上下文 `ctx`
- `ctx` 提供：
  - 设备 udid
  - 平台
  - app_id
  - version
  - 当前账号态
  - Appium 操作封装

脚本失败分两类：

1. 断言失败
2. 脚本执行异常

两类都应触发 agent 回退，但结果中要保留 `script_error` 供观察。

## 与现有批次执行的衔接

当前批次执行机制保留不变：

- 同设备仍按原顺序执行
- 设备间仍可并行
- 批次仍按固定大小切分
- 账号态仍通过 `account_<udid>.txt` 在批间传递

新增逻辑只影响“单条 case 执行器”的选择，不改变：

- 分组逻辑
- 切批逻辑
- 批次回写逻辑

## 与探索链路的关系

探索链路仍保留，但其职责只负责：

- 更新 `apps/gaotu/index.md`
- 补充页面知识与页面 XML

探索链路不直接生成 case 脚本。

case 脚本只来源于“真实执行通过的结果”，避免把探索阶段的页面快照误当作可执行脚本。

## 失败回退策略

若命中脚本：

1. 先执行脚本
2. 若脚本通过：
   - 直接产出结果
   - 不再调用 agent
3. 若脚本失败：
   - 记录脚本失败原因
   - 立即回退 agent
4. 若 agent 通过：
   - 用最新结果覆盖重生成脚本
5. 若 agent 失败：
   - 保留 agent 结果
   - 不更新脚本

## 数据兼容性

结果表与报告层需要能区分来源：

- `script`
- `agent`
- `script_fallback_agent`

但外部展示默认不必大改，可先在结果对象里增加内部字段，不立即暴露到飞书表列。

## 测试策略

至少补以下自动化测试：

1. 通过结果可生成脚本文件
2. 失败结果不会生成脚本
3. 仅低可信视觉断言的结果不会生成脚本
4. 命中脚本时优先执行脚本
5. 脚本失败时会回退 agent
6. agent 回退通过后会覆盖脚本
7. 单设备顺序执行时，脚本命中不会打乱原有顺序

## 风险与约束

### 风险 1：结果证据不足导致脚本不可生成

应接受“部分 case 仍长期为 agent-only”的现实，不强制 100% 脚本化。

### 风险 2：脚本老化

页面改版后脚本可能失效，因此必须保留回退 agent 的兜底。

### 风险 3：前置表达不足

如果当前结果无法稳定描述“如何到达该页面”，脚本应放弃生成，而不是生成脆弱脚本。

## 实施范围

第一阶段只做：

- Android
- 单条 case 独立脚本
- 通过 case 固化
- 脚本优先、失败回退 agent
- 最小可运行脚本执行器

第二阶段再考虑：

- iOS
- 失败 case 复现脚本
- 脚本健康度统计
- 脚本覆盖率面板

## 验收标准

满足以下条件视为完成：

1. 首次 agent 跑通某 Android case 后，会生成 `apps/gaotu/cases/android/<record_id>.py`
2. 下次执行同 case 时，优先跑该脚本
3. 脚本通过时，不再调用 agent
4. 脚本失败时，会自动回退 agent
5. agent 回退通过后，会更新该脚本
6. 不影响现有设备分组、批次执行、结果回写能力
